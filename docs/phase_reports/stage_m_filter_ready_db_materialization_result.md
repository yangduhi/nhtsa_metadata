# Stage M Filter-Ready DB Materialization Result

## Purpose

Materialize a GUI-facing filter database from the existing 2011+ metadata-only
SQLite output without modifying the source output database.

The materialized database is intended for `nhtsa_gui` import. It includes vehicle
specification filter fields and test-level barrier load-cell classification
results only. It intentionally does not retain per-channel load-cell detail rows.

## Inputs

- Source DB:
  `data/full_2011plus_metadata_only_refresh_2026-05-03.sqlite`
- Output DB:
  `data/full_2011plus_metadata_filter_ready_2026-05-04.sqlite`
- Load-cell config:
  `docs/nhtsa_barrier_load_cell_classification_config_v2.2.2.json`

The source DB remains unchanged. The output DB is an ignored runtime artifact and
is not committed.

## Code Changes

- Added `nhtsa_metadata.services.filter_db_materializer`.
- Added CLI command:
  `nhtsa-metadata schema materialize-filter-db`.
- Added regression coverage for:
  - source DB copy behavior
  - vehicle specification promotion from raw vehicle payload fields
  - test-level load-cell classification summary materialization
  - omission of load-cell channel-map detail rows from the filter-ready DB

## Load-Cell Detail Policy

The filter-ready DB does not retain load-cell channel-map detail rows.

Excluded from the GUI transfer contract:

- per-channel load-cell rows
- row/column/pole index
- force/moment channel detail
- curve number
- channel axis/unit
- instrumentation commentary/detail

The GUI-facing value is only the test-level load-cell classification result.

## Remaining Risks

- The filter-ready SQLite file is an ignored runtime artifact. Consumers must be
  pointed at the generated output DB path or another DB generated by the same
  command.
- The current `has_load_cell_barrier` count is 1,149, while classifier-backed
  load-cell classified tests are 1,137. The difference is fallback metadata
  evidence from barrier shape/commentary and should remain visible as a boolean
  filter distinction.
